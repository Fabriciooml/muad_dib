# Configurable Cinema Session Tracker — V1 Design

## Goal

Discover newly listed sessions for configured watches. Each watch request names a movie title, optional `providers` list, optional city/cinema/room name filters, and its own polling interval. Omitted `providers` means all registered providers, including adapters added after watch creation. Provider-specific movie ID is resolved and stored internally. Interval defaults to 15 minutes on creation. Persist sessions in PostgreSQL and publish each discovery to Kafka. First watch to create through admin interface: Cineart movie `23469` (Duna - Parte Três), Cineart Boulevard, Sala 06 IMAX. On first successful poll after a watch is created, publish matching sessions not already recorded globally. No ticket-sale availability tracking or user notification.

## Source and identification

Provider seam: `resolve_movie(title: str) -> MovieMatch` and `fetch_sessions(movie_id: str) -> list[Session]`. A provider adapter owns title lookup, source requests, parsing, source-specific identifiers, and conversion to a common `Session` value. V1 implements only Cineart. A simple provider registry in application composition maps `"cineart"` to its adapter. Provider selection is shared by watch creation/replacement and previews: omitted `providers` selects all registered adapters, while an explicit nonempty list selects exactly those names. Duplicate names collapse; unknown names or an empty list return 422. A later Cinemark adapter can implement the same interface without changing scheduler, database, outbox, or event publisher. No generic scraping framework or dynamic plugin loading.

Shared `SessionInspector` owns provider expansion, title resolution, live fetch, normalized location matching, and per-provider results. It accepts cached provider targets for scheduled watches and no targets for previews. `resolve_targets()` supplies POST/PUT without fetching sessions; `inspect()` supplies scheduler and preview routes. Inspector performs source requests but never writes PostgreSQL, changes schedules, or publishes Kafka. Scheduler persists inspection results and updates target state; previews serialize results or compare identities to PostgreSQL. This keeps discovery rules in one module.

Cineart title resolver reads Cineart's film listing pages (`/em-cartaz`, `/estreias`, `/em-breve`) and extracts each film title and `/filme/{id}` link. On September 30, 2026, `/em-breve` listed `Duna - Parte Três` with `/filme/23469`. Repeated listings for the same film ID collapse into one candidate. For one provider, a missing title is a not-found result; multiple normalized exact-title matches with different IDs are ambiguous; a source failure is a source-error result. Cross-provider handling is defined below. Watch creation succeeds even when no provider lists the film yet. Unresolved providers stay pending on that watch and are retried on future polls; response makes pending status explicit. Resolver never silently picks a fuzzy match. Resolved movie IDs stay cached on the watch; title lookup repeats only for pending providers or changed watch title. Cineart adapter fetches `https://cineart.com.br/filme/{movie_id}` once per distinct configured movie per poll. The server-rendered HTML contains a `filme-prog` element whose `:cinemas` attribute is HTML-escaped JSON. In the observed response for `23469`, cinema key `25` is Cineart Boulevard; its Sala 06 IMAX entry has room key `8201`, `SALA` = `Sala 06 IMAX`, and each matching showtime has `IMAX` = `1`. Room grouping keys are advisory. Adapter returns sessions for every city, cinema, and room on that movie page; shared watch matching applies optional filters. Extract date, local time (minute precision), city, cinema ID/name, room, language, format, and `URL_COMPRA`. Cineart times use `America/Sao_Paulo`.

As observed on September 30, 2026, six matching sessions were present: December 15 and 16, at 14:00, 17:20, and 20:40 each. Their purchase links do not establish whether tickets can already be bought.

An explicit "Sessões ainda não disponíveis para esse filme" page means zero sessions. Missing or malformed session data without that message is a poll failure, never a deletion. Existing sessions may disappear or change URL; V1 updates URL/metadata when seen again but emits no removal or change event. A changed date or minute is a new session. Matching compares provider and movie ID exactly; supplied city, cinema, and room names are trimmed and compared case-insensitively. Omitted filters match all. Overlapping watches produce one discovery per physical session.

## Runtime

Use Python 3.11+ with `python-components` 0.4.x, `fastapi-component`, `kafka-component`, `prometheus-component`, and `postgres-component` 0.1.x. `fastapi-component` owns a `System` with `PostgresComponent`, Kafka producer, metrics, poller, and outbox publisher. `PostgresComponent` owns async SQLAlchemy engine/session lifecycle and fail-fast connection check; app-owned `PostgresStore` runs parameterized SQLAlchemy Core queries through `database.session()`. FastAPI exposes `/health/live`, `/health/ready`, `/metrics`, and internal watch CRUD routes. Readiness uses PostgreSQL component state and a fresh dependency check. Watch routes require `X-Admin-Token` matching `ADMIN_API_KEY` from environment; no browser-facing auth or frontend in V1. Deploy through a Portainer Docker Standalone stack with one process, one Uvicorn worker, and one replica for V1. Build and tag image before Portainer deployment; stack pulls it from a registry reachable by Portainer host. HTTP binds to host loopback by default, with bind address configurable in Portainer. No public ingress is required.

Scheduler checks PostgreSQL for due enabled watches at startup and every 30 seconds. Each due watch expands its selected providers from the current registry; omitted selection includes newly added adapters. Each provider has a persisted target state and resolved movie ID when known. Unresolved targets retry title resolution on later due polls without blocking resolved targets. Fetch failures retain resolved IDs and retry fetch on the next due poll. A new watch is due immediately. Each watch stores `next_poll_at`; after a successful fetch/save or a source fetch failure, scheduler sets it to completion time plus that watch's interval. A failed fetch remains visible in metrics and is retried at its next due time. A database write failure leaves watch due for the next scheduler check. Restart preserves schedule from PostgreSQL. Only due watches participate in each cycle; group resolved targets by `(provider, movie_id)` and fetch each movie once even when several due watches share it. Reschedule a watch after all selected provider attempts finish; database write failure leaves it due for retry. Polls never overlap; one provider failure does not suppress independent providers or watches. HTTP requests have a timeout. PostgreSQL stores session identity and first-seen time. Each newly inserted session creates a JSON outbox record in the same transaction. An independent publisher sends pending records through `KafkaProducerComponent.send()`, then marks each published after Kafka acknowledgement. Failure leaves it pending for retry. A crash after acknowledgement can redeliver; stable event IDs enable downstream deduplication.

## Persistence and event contract

Formal JSON Schema for session result, preview response, and Kafka discovery payload: [`schemas/output.v1.schema.json`](../../../schemas/output.v1.schema.json). `purchase_url` is required in every session output. Preview `/new` uses the same response shape as `/sessions/preview`; only its `sessions` array differs.

Watch table stores UUID ID, submitted movie title, nullable provider selection (`NULL` means dynamic all; explicit nonempty array means fixed list), optional city/cinema/room name filters, enabled flag, `poll_interval_minutes` (positive integer, default `15`), `next_poll_at` (UTC), `revision` (incremented on replacement/disable), and timestamps. Index enabled watches by `next_poll_at`; enforce `revision >= 1` and `providers IS NULL OR cardinality(providers) > 0`. A `watch_provider_targets` table has primary key `(watch_id, provider)`, cascading watch deletion, nullable resolved movie ID, resolution status (`resolved`, `pending_not_found`, `pending_source_error`, or `pending_ambiguous`), last resolution attempt, last fetch attempt, last successful fetch, and last fetch error. Enforce `resolved` iff movie ID is present; pending states require a null movie ID. Fetch failure never clears a resolved movie ID. New adapters for dynamic-all watches get target rows at the next due poll. Scheduler locks due watch rows in one PostgreSQL transaction, compares stored revisions with inspected revisions, then recomputes the session union from matching enabled watches, inserts discoveries/outbox rows, updates their target states, and reschedules them before commit. This prevents concurrent PUT/disable/delete from publishing stale matches or overwriting a new schedule. Internal API: `GET /watches`, `GET /watches/{id}`, `POST /watches`, `PUT /watches/{id}`, and `DELETE /watches/{id}`. `POST` validates provider selection and required movie title, attempts resolution in every selected provider, fills default interval, and sets `next_poll_at` to now. `PUT` requires full editable watch definition including title and interval, retains matching resolved targets when title/provider selection are unchanged, otherwise resolves changed targets, then replaces fields, and resets `next_poll_at` to now so changes take effect promptly. `DELETE` removes watch but preserves discovered sessions. Scheduler sees created or changed watches within 30 seconds without redeployment. Adding overlapping watches does not re-emit sessions already recorded.

Example POST body: `{"providers":["cineart"],"movie_title":"Duna - Parte Três","cinema":"Cineart Boulevard","room":"Sala 06 IMAX"}`. Omit `providers` to include every registered provider now and in future. Optional `city` can narrow a broader name match. `enabled` defaults to `true`; `poll_interval_minutes` defaults to `15`. Response is 201 with watch UUID, requested `providers` selection, per-provider target statuses and read-only resolved movie IDs, stored fields, and `next_poll_at`. Clients never need to submit movie IDs. Required strings and supplied filters cannot be blank. Unknown/empty provider list or nonpositive/noninteger interval returns 422. POST/PUT create or replace watch with pending targets when selected providers report not found or source errors, even when none resolves yet. Ambiguous title in a selected provider returns 409 with candidates and does not change watch. Successful response returns 201 for POST or 200 for PUT with per-provider statuses; pending targets retry later. Cineart numeric cinema ID remains an internal session identity field, not a watch request filter.

## Read-only session previews

Both internal GET routes require `X-Admin-Token` and accept required `movie_title`, repeatable optional `providers` query parameters, plus optional `city`, `cinema`, and `room`. Omitted `providers` uses every currently registered provider for that request. They use the same provider title resolution, live session fetch, and normalized location matching as a watch. Polling interval is irrelevant. A shared `SessionFilter` implements matching for watches and previews.

- `GET /sessions/preview` returns every currently listed matching session across selected providers.
- `GET /sessions/preview/new` returns only currently listed matching sessions whose stable session identity is absent from the global PostgreSQL `sessions` table. Existing sessions discovered through any watch count as known.

Example: `GET /sessions/preview?providers=cineart&movie_title=Duna%20-%20Parte%20Tr%C3%AAs&cinema=Cineart%20Boulevard&room=Sala%2006%20IMAX`. Replace path with `/sessions/preview/new` for only globally unseen sessions. Omit `city`, `cinema`, or `room` to broaden results.

Both return 200 with requested provider selection, per-provider resolution/fetch statuses and resolved IDs, applied filters, UTC `checked_at`, total `count`, and provider-tagged `sessions` containing date, time, timezone, city, cinema, room, format, language, and `purchase_url`. Results are sorted by date/time and location. Responses use `Cache-Control: no-store`. Requests create no watch, session, outbox record, schedule change, or Kafka event. `/new` reads existing identities from PostgreSQL; its answer is a snapshot, not a reservation, and a concurrent poll can insert the same session after comparison. Provider/title/filter validation matches watch creation. Successful providers return sessions even when another provider reports no movie, ambiguity, or a source failure; response marks `partial: true` and lists each provider status. If none succeeds, return 404 for all-not-found, 409 for ambiguity, or 503 for source failure. A provider fetch or parse failure is never presented as an empty successful provider result.

Session uniqueness: `(provider, movie_id, cinema_id, room_key, session_date, session_time)`; `room_key` is normalized with `strip().casefold()`, while `room_name` preserves latest display value. `session_time` is normalized to `HH:MM` before persistence. IDs are provider-scoped strings. Cineart payload inspection found no durable showtime ID, so V1 uses this composite key. A genuine room rename can create a new identity; a later provider with durable IDs needs a migration. Never use purchase URL as identity. `sessions.purchase_url` is a required `TEXT` column holding the source's direct purchase URL. Polls update this column when an existing session's URL changes, without emitting a new discovery. Each session has a UUID primary key and first-seen timestamp. Outbox rows reference that session and keep immutable discovery payloads. Index unpublished outbox rows by `(created_at, id)` and give `(session_id, topic)` a unique constraint. Outbox topic: `cinema.sessions.discovered.v1`. One event per new session, including first-run discoveries. Kafka key: stable session identity encoded as UTF-8. JSON value: `event_id` (outbox UUID), `event_type` (`session.discovered`), `schema_version` (`1`), `observed_at` (UTC ISO 8601), `provider`, `movie_id`, `city`, `cinema_id`, `cinema`, `room`, `date`, `time`, `timezone`, `format`, `language`, and `purchase_url` as observed on discovery.

Production PostgreSQL and Kafka exist outside tracker stack. A separate local Compose file starts optional PostgreSQL and Kafka for development and tests. V1 owns an Alembic revision for schema creation; `postgres-component` supplies `migration_wiring()` and `create_migration_engine()` but does not run migrations. Portainer stack has a one-shot `alembic upgrade head` service using the same image, and tracker service depends on successful migration completion. `DATABASE_URL` uses SQLAlchemy's `postgresql+asyncpg://` scheme. Portainer environment configuration supplies `DATABASE_URL`, `KAFKA_BOOTSTRAP_SERVERS`, `ADMIN_API_KEY`, `TRACKER_IMAGE`, and optional host bind address (`127.0.0.1`) and port (`8000`). No credentials or production endpoint values go into Compose source. Kafka topic and 30-second scheduler check cadence are V1 constants; polling interval belongs to each watch.

## Acceptance

- Against the saved Cineart fixture, first poll inserts and emits six sessions; repeat poll emits zero. Live session count may change.
- Two watches for same movie fetch once; optional location filters select correct sessions; overlapping watches emit once.
- Omitted `providers` on watch persists dynamic all; adapter added later joins at next due poll. Explicit provider list stays fixed. Pending provider does not block resolved provider; its title lookup retries later.
- Preview GETs accept repeated `providers` parameters; omitted selection tries all currently registered providers. Mixed provider outcomes report per-provider status and mark partial results.
- Unknown provider selection returns 422; ambiguous title returns 409 without changing a watch. No-match or source-error targets remain pending; adapter failure leaves successful providers and other watches runnable.
- Unauthorized watch requests return 401; CRUD changes are visible on next poll and never require Portainer redeploy.
- Both preview routes require admin token, return live matching sessions with purchase URLs, and leave watches, sessions, outbox, schedules, and Kafka unchanged. `/sessions/preview/new` excludes sessions already stored through any watch and returns same candidates on repeated calls until a real poll persists them.
- POST without interval stores 15 minutes; custom positive interval schedules separately. PUT reschedules immediately; restart preserves `next_poll_at`.
- A later new date/time inserts one session and emits one event.
- Reordered HTML data, changed purchase URL, or seconds-only time differences do not create duplicate events.
- Storage reads return persisted purchase URL; later URL changes update stored session while preserving original discovery event.
- Unavailable-page response leaves existing rows intact. Malformed page, HTTP failure, database failure, or Kafka failure never marks an undispatched event published.
- `/metrics` exposes poll and publish counters, last-success time, and pending outbox count. Health endpoints reflect process and dependency state.
- Unit tests use saved HTML fixtures, not live Cineart. PostgreSQL/Kafka integration tests exercise transaction and acknowledgement behavior. Live source check is manual and read-only.
